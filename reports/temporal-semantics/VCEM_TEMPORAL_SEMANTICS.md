## Implementation semantics

`revokeConsent` becomes authoritative when its transaction executes successfully in ledger order. During execution it appends a new consent version, sets that version to `REVOKED`, clears the actor set for the new version, updates `_currentVersion`, and emits the lifecycle events. Client submission and mempool acceptance do not alter contract state.

`authorizeAndLogAccess` reads `getCurrentConsentVersion` during its own transaction execution. It first requires that the current status is `ACTIVE`, then compares the current `consentHash` with the signed `expectedConsentHash`, followed by actor, purpose, scope, and registered-data checks. Consequently:

- after revocation, authorization is rejected first as `VCEMAudit: consent inactive`;
- after an active update, a request signed against the prior version is rejected as `VCEMAudit: outdated consent hash`;
- an authorization ordered before revocation may succeed and remains valid historical evidence; revocation is not retroactive.

`expectedConsentHash` detects a request that is stale when a newer active consent version is already authoritative. It does not reserve transaction priority, prevent miners/validators from ordering a pending authorization before a pending transition, or protect against mempool front-running. VCEM has no private-mempool or revocation-priority mechanism.

## Deterministic ordering results

Eight scenarios were generated by deploying a fresh VCEM fixture for each condition. Adjacent-block cases used ordinary receipt waits. Same-block cases disabled Hardhat automining, submitted transactions from separate participant/gateway accounts, and mined one block explicitly. Equal fees preserved submission order in cases 5A and 5B; cases 5C and 5D used controlled fee priority to create both reversals between submission order and finalized transaction order.

| Case | Finalized evidence | Result |
| --- | --- | --- |
| Authorization before revocation | authorization block 10/index 0; revocation block 11/index 0 | Authorized under version 1; historical event retained |
| Revocation before authorization | revocation block 21/index 0 | Authorization rejected: `VCEMAudit: consent inactive` |
| Request prepared before revocation, processed after | revocation block 32/index 0 | Stale signed request rejected: `VCEMAudit: consent inactive` |
| Old request after active update | update block 43/index 0 | Rejected: `VCEMAudit: outdated consent hash` |
| Same block, authorization then revocation | block 54, authorization index 0, revocation index 1 | Authorized under version 1 |
| Same block, revocation then authorization | block 64, revocation index 0, authorization index 1 | Authorization receipt status 0; `VCEMAudit: consent inactive` |
| Revocation submitted first, authorization ordered first | block 74, authorization index 0, revocation index 1 | Authorization succeeded under version 1, proving submission time is not authoritative |
| Authorization submitted first, revocation ordered first | block 84, revocation index 0, authorization index 1 | Authorization receipt status 0; `VCEMAudit: consent inactive` |

Exact transaction hashes, consent hashes, block numbers, and transaction indices are in `temporal-ordering-results.csv` and `raw/hardhat-temporal-ordering-evaluated-6077d27.json`.

## Revocation-to-enforcement latency

The experiment definition was the monotonic elapsed wall-clock time immediately before submitting a valid `revokeConsent` transaction through the configured RPC endpoint until its successful receipt/finality with one confirmation. In this IBFT deployment, successful block inclusion provides deterministic finality under the assumed healthy-validator model. The statistical unit was one independent revocation trial.

- n: 20
- Run-level values (ms): 2001.564, 2007.251, 2022.354, 1992.569, 1720.239, 1994.874, 2006.048, 1987.122, 2025.010, 1991.778, 1986.985, 1718.324, 1998.697, 2048.649, 1795.098, 1999.110, 1995.436, 1986.888, 2005.025, 1991.997
- Arithmetic mean: 1963.751 ms
- Sample standard deviation: 96.700 ms
- Median: 1995.155 ms
- Minimum: 1718.324 ms
- Maximum: 2048.649 ms
- p95: 2025.010 ms (nearest-rank empirical percentile)

Each trial used a distinct participant ID and active consent. A valid authorization request was signed before revocation. After the revocation receipt, the stale authorization was submitted as an actual transaction. RPC re-verification confirmed 20/20 successful revocation receipts, 20/20 stale authorization receipts with status 0, and 20/20 rejection reasons equal to `VCEMAudit: consent inactive`. Every stale authorization was ordered after its corresponding revocation.

## Direct answers to Concern 9

1. Revocation becomes effective at successful transaction execution/inclusion in finalized ledger order, not at submission or mempool acceptance.
2. Authorization finalized before revocation can succeed under the then-current active consent and is not retroactively invalidated.
3. Revocation finalized before authorization causes the authorization to fail because the current status is `REVOKED`.
4. A request signed against an old active version fails after an update through `expectedConsentHash`; after revocation the earlier status check rejects it first.
5. `expectedConsentHash` detects stale active-state references. It does not prevent transaction-ordering races or grant revocation priority.
6. VCEM does not itself protect a pending revocation from mempool reordering/front-running.
7. In the specified co-located Besu environment, submission-to-receipt revocation latency had mean 1963.751 ms and sample SD 96.700 ms across 20 trials.
8. Edge cases were generated with fresh deployments/participants, pre-signed requests, controlled automining, explicit same-block mining, transaction-index checks, and deliberate fee-priority ordering reversals in both directions.

## Limitations

- The measured latency is host-, network-, RPC-polling-, and block-phase-dependent; it is not a universal VCEM latency bound.
- One receipt confirmation was used, matching the evaluated local setup. This report does not model validator compromise or reconfiguration.
- The same-block ordering evidence uses deterministic Hardhat mining against the exact evaluated contract source. The latency evidence uses the actual five-node Besu IBFT deployment.
- No claim is made that client timestamps represent consensus time. Ordering evidence relies on block number and transaction index.
- This experiment does not establish production clinical deployment or legal compliance.

## Reproduction

```bash
npm run test:temporal
npm run besu:up
npm run besu:status
npm run experiment:temporal:besu
```

For exact evaluated-source reproduction, compile commit `6077d27a9eca686e5395e8e081bbbf588b824a0b` and set `VCEM_EVALUATED_ROOT` to that worktree before the Besu command. The runner refuses a worktree whose HEAD differs from the evaluated commit and requires exactly 20 trials.
